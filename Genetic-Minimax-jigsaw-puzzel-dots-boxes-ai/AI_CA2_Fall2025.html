def roulette_selection(population: List[Individual], elite_size: int) -> List[Tuple[Individual, Individual]]:
    if len(population) <= elite_size:
        # Not enough individuals to do anything 
        return []

    # First we rank everyone based on fitness, descending
    sorted_pop = sorted(population, key=lambda x: x.fitness, reverse=True)

    # We're ignoring elites — assuming they survive automatically
    remaining = sorted_pop[elite_size:]

    # Create a simple list of fitness values
    fit_vals = []
    for indiv in remaining:
        fit_vals.append(indiv.fitness)

    total_fit = sum(fit_vals)

    # fallback — if all fitnesses are 0, we'll just assign flat probabilities
    if total_fit == 0:
        fit_vals = [1.0 for _ in remaining]
        total_fit = float(len(fit_vals))

    # Build up a cumulative list for roulette wheel
    cumulative_probs = []
    tally = 0.0
    for val in fit_vals:
        tally += val
        cumulative_probs.append(tally)

    # Helper function to simulate a spin of the wheel
    def spin_the_wheel():
        spin_val = random.uniform(0, total_fit)
        chosen_idx = bisect_left(cumulative_probs, spin_val)
        if chosen_idx >= len(remaining):
            # shouldn't happen, but just in case
            chosen_idx = len(remaining) - 1
        return remaining[chosen_idx]

    # We'll pair up individuals, skiping elites
    pairs_to_form = (len(population) - elite_size) // 2
    parent_pairs = []

    for _ in range(pairs_to_form):
        # Note: might end up with same individual twice
        first = spin_the_wheel()
        second = spin_the_wheel()
        parent_pairs.append((first, second))

    return parent_pairs

Task: Implement the Crossover Logic

Crossover is where the "genetic" part of the algorithm happens. You'll create a new "child" individual by combining the traits of two "parent" individuals. The goal is to build a better-assembled puzzle by picking the best-fitting pieces from the parents.

This crossover strategy is complex. It starts with a random piece and then iteratively adds adjacent pieces based on a priority system.

Crossover Priority System:

  1. Shared Pieces (Highest Priority): If two parents agree on a neighboring piece, that piece is chosen. This is a strong indicator of a correct fit.
  2. Buddy Pieces (Medium Priority): A "buddy piece" is a pair of pieces that are each other's best match. If one of these is a neighbor, it's a good candidate.
  3. Best Match (Lowest Priority): If neither of the above is found, choose the piece that has the lowest dissimilarity score (the best fit) from the remaining pieces.

  1. Implement Piece Selection Methods:

  2. Implement the Crossover Class:

    def _initialize_kernel(self):

            return self._analysis.get_dissimilarity((base_id, neighbor_id), "L-R")
        elif orientation == "L":
            return self._analysis.get_dissimilarity((neighbor_id, base_id), "L-R")
        elif orientation == "D":
            return self._analysis.get_dissimilarity((base_id, neighbor_id), "T-D")

    def _neighbor_in_parent(self, parent, piece_id, orientation):
        grid = parent._chromosome.reshape(parent._rows, parent._columns)
        rows, cols = grid.shape
        
        # Find the (row, col) of the current piece
        r, c = -1, -1
        
        found = False
        for i in range(rows):
            for j in range(cols):
                if grid[i, j] == piece_id:
                    r, c = i, j
                    found = True
                    break
            if found:
                break
        
        if not found:
            return None

        nr, nc = r, c
        if orientation == "T-D": # Top-Down (Bottom neighbor)
            nr += 1
        elif orientation == "L-R": # Left-Right (Right neighbor)
            nc += 1
        elif orientation == "B-T": # Bottom-Top (Top neighbor)
            nr -= 1
        elif orientation == "R-L": # Right-Left (Left neighbor)
            nc -= 1
            
        # Check boundaries
        if 0 <= nr < rows and 0 <= nc < cols:
            return grid[nr, nc]
            
        return None
    def _add_candidate_to_heap(self, priority: int, piece_id: int, position: tuple, relative_piece: tuple):
        heapq.heappush(self._candidate_pieces, (priority, (position, piece_id), relative_piece))

    def _available_boundaries(self, row_and_column):

        boundaries = []
        if not self._is_kernel_full():
            positions = {"T": (row - 1, column), "R": (row, column + 1), "D": (row + 1, column), "L": (row, column - 1)}

import random

def mutation(individual: Individual, mutation_rate: float = 0.01) -> Individual:
    # Flatten the chromosome to a 1D list of piece ids
    genes = individual._chromosome.flatten().tolist()
    length = len(genes)

    # For each gene, with probability mutation_rate, swap with another random gene
    for i in range(length):
        if random.random() < mutation_rate:
            j = random.randrange(length)
            genes[i], genes[j] = genes[j], genes[i]

    # Create a new Individual with the mutated chromosome
    mutated = Individual(
        pieces=individual.pieces,
        rows=individual._rows,
        columns=individual._columns,
        initial_state=genes,
        analysis=individual.analysis
    )
    return mutated

Question 3: Inadequacy of Simple Crossover for Permutations

  • The jigsaw puzzle problem uses a chromosome that is a permutation of unique piece IDs.

  • The essential constraint for this problem is that every piece ID must appear exactly once in the child chromosome.

  • Simple crossover methods, such as one-point or two-point crossover, are designed for binary strings or non-unique integer arrays.

  • When these methods are applied to a permutation:

    • They copy segments from one parent and combine them with segments from the second parent.
    • This process frequently results in illegal chromosomes.
    • The child will contain duplicate piece IDs (genes) and be missing other unique piece IDs.

  • An illegal chromosome (a chromosome that is not a complete permutation) does not represent a valid puzzle arrangement.

  • Using these invalid solutions fundamentally breaks the genetic algorithm's search space and prevents meaningful convergence.

  • Therefore, complex, permutation-specific operators (like the Heuristic Crossover) are necessary to maintain the integrity of the chromosome (the complete set of unique piece IDs) while combining the local ordering information from the parents.

Question 4: Selection Pressure and Genetic Diversity

  • The process of selection in a Genetic Algorithm involves choosing the fittest individuals to reproduce for the next generation.
  • Selection Pressure refers to the degree to which fitter individuals are favored over weaker ones during this process.

High Selection Pressure and Premature Convergence

  • High Selection Pressure (like focusing on the very top individuals) strongly favors the very best solutions found early on.

  • This pressure quickly pushes the population toward focusing on the current best individuals.

  • leading to a rapid loss of Genetic Diversity, that results in the population becoming homogeneous (all individuals look alike). The algorithm then struggles to escape local optimum because it lacks the necessary variation to explore new regions of the search space , aka, premature convergence, where the algorithm stops improving before finding the true best solution (global optimum).

  • NOTE: Genetic Diversity is crucial because it ensures the algorithm retains traits that might be necessary later to solve difficult parts of the puzzle or escape a local optimum.

Maintaining Diversity with Tournament Selection

  • Tournament Selection helps maintain diversity by introducing an element of chance in survival.
  • In tournament selection, a small group (the tournament) is randomly chosen, and the best individual within that small group wins a spot as a parent.
  • This mechanism allows weaker individuals (those not among the top elites of the whole population) to compete within their small, randomly chosen group and still have a chance of survival.
  • By allowing slightly weaker solutions to pass their genes to the next generation, Tournament Selection slows down the convergence and preserves more genetic material, ultimately leading to better global exploration and a higher chance of finding the true optimal solution.

Question 5: Role of Swap Mutation and Mutation Rate Risks

  • Swap Mutation is a mutation operator specifically designed for permutation problems (like the jigsaw puzzle).
  • It works by randomly selecting two positions in the chromosome (the list of piece IDs) and swapping the pieces at those positions.
  • This is essential because it maintains the core constraint of the problem: the chromosome remains a complete and valid permutation (no pieces are duplicated or lost).

Role of Mutation (General)

  • The primary role of mutation is to reintroduce genetic diversity into the population.
  • It prevents the population from becoming stuck in a local optimum by allowing the search to explore entirely new regions of the search space that might not be reachable through crossover alone.

Risks of Mutation Rate

  • Very Low Mutation Rate:
    • The algorithm runs the risk of premature convergence to a local optimum.
    • The lack of diversity means the population quickly becomes homogeneous (similar chromosomes).
    • Once stuck, there are not enough random changes to help the search escape the local optimum and find the global best solution.
    • Exploration is effectively halted, leading to suboptimal results.
  • Very High Mutation Rate:
    • The algorithm essentially degrades into a random search or random walk through the search space.
    • The beneficial structures (good local piece pairings) created by the efficient Crossover operator are destroyed almost immediately by the high rate of random swapping.
    • The algorithm loses its memory and fails to build upon the improvements of past generations, making the process inefficient.

class TestMinimaxAgent:
    """A configurable Minimax class for testing purposes, tracks nodes and time."""
    def __init__(self, isPlayer1: bool, use_pruning: bool = True):
        self.isPlayer1 = isPlayer1
        self.use_pruning = use_pruning
        self.nodes_searched = 0
        self.move_time_total = 0.0
        self.move_count = 0

    def heuristic(self, state: GameState) -> float:
        """Simple heuristic: Difference in scores."""
        p1, p2 = state.get_scores()
        score = p1 - p2 if self.isPlayer1 else p2 - p1
        return float(score)

    def minimax(self, state: GameState, depth: int, alpha: float, beta: float, maximizing: bool) -> float:
        self.nodes_searched += 1
        
        if depth == 0 or state.is_gameover():
            return self.heuristic(state)

        moves = state.available_moves()
        
        if maximizing:
            max_eval = -float('inf')
            for mtype, pos in moves:
                new_state = state.clone()
                scored = new_state.apply_move(mtype, pos)
                
                next_turn_maximizing = maximizing if scored else not maximizing
                eval_val = self.minimax(new_state, depth - 1, alpha, beta, next_turn_maximizing)
                max_eval = max(max_eval, eval_val)
                
                if self.use_pruning:
                    alpha = max(alpha, eval_val)
                    if beta <= alpha:
                        break
            return max_eval
        else:
            min_eval = float('inf')
            for mtype, pos in moves:
                new_state = state.clone()
                scored = new_state.apply_move(mtype, pos)
                
                next_turn_maximizing = not maximizing if not scored else maximizing
                
                eval_val = self.minimax(new_state, depth - 1, alpha, beta, next_turn_maximizing)
                min_eval = min(min_eval, eval_val)
                
                if self.use_pruning:
                    beta = min(beta, eval_val)
                    if beta <= alpha:
                        break
            return min_eval

    def choose_move(self, state: GameState, max_depth: int) -> Tuple[Any, Any, float]:
        start_time = time.perf_counter()
        
        best_move = None
        best_val = -float('inf')
        alpha = -float('inf')
        beta = float('inf')
        
        moves = state.available_moves()
        random.shuffle(moves)
        
        for mtype, pos in moves:
            new_state = state.clone()
            scored = new_state.apply_move(mtype, pos)
            
            is_max = True if scored else False
            
            val = self.minimax(new_state, max_depth - 1, alpha, beta, is_max)
            
            if val > best_val:
                best_val = val
                best_move = (mtype, pos)
            
            if self.use_pruning:
                alpha = max(alpha, val)
        
        elapsed = time.perf_counter() - start_time
        self.move_time_total += elapsed
        self.move_count += 1
        
        return (*best_move, best_val) if best_move else (None, None, 0.0)

def play_match(agent_algo, agent_random, board_size, depth):
    """Plays a single game between two specified agents and returns stats."""
    # Reset stats
    agent_algo.nodes_searched = 0
    agent_algo.move_time_total = 0
    agent_algo.move_count = 0
    
    state = make_initial_state(board_size, player1_starts=True)
    
    while not state.is_gameover():
        if state.player1_turn:
            mtype, pos, _ = agent_algo.choose_move(state, max_depth=depth)
            if mtype: scored = state.apply_move(mtype, pos)
            else: break
        else:
            mtype, pos, _ = agent_random.choose_move(state)
            if mtype: scored = state.apply_move(mtype, pos)
            else: break
            
        # Manually manage turn change if no score was made
        if not scored:
             state.player1_turn = not state.player1_turn

    p1, p2 = state.get_scores()
    return p1 > p2, agent_algo.nodes_searched, agent_algo.move_time_total, agent_algo.move_count

Question 2: Move Ordering and Alpha-Beta Pruning Efficiency

  • The order in which the Minimax algorithm explores child moves is critical for the efficiency of Alpha-Beta Pruning.

  • The goal is to find the best move as early as possible within the search.

  • Finding the best move early narrows the Alpha-Beta window quickly, leading to the maximum possible number of cutoffs (pruning).

  • The provided _order_moves method is a strong game-specific heuristic.

  • It prioritizes moves that complete a box and give an extra turn (Completing Moves).

  • These moves are critical to search first as they maximize the immediate gain, quickly raising the Alpha bound for the maximizing player.

  • The subsequent ranking of Safe Moves over Risky Moves effectively uses game knowledge.

  • This ensures the agent minimizes creating obvious scoring opportunities for the opponent, thereby avoiding unnecessary deep searches down bad branches.

  • A key strategy for further improvement is using a Transposition Table or Killer Moves.

  • A Killer Move is a move that caused an Alpha-Beta cutoff (pruning) in a sibling node at the same search depth.

  • If a move was effective at pruning one branch, it is highly likely to be effective at pruning another.

  • An improved search order would be: Completing Moves, then Killer Moves(if stored), followed by Safe Moves, and finally Risky Moves.

# # Question 3: Branching Factor # #

  • The Branching Factor (b) of a game state is the number of legal moves available to the current player from that state.
  • It measures the "bushiness" of the game tree and directly determines the complexity of the Minimax search (O(bd), where d is depth).

Change in Branching Factor during Dots and Boxes

  • The Branching Factor in Dots and Boxes is initially high but generally decreases throughout the game.

  • Beginning of the Game (Empty Board):

    • The Branching Factor is at its maximum. For an n × n grid of boxes (with (n+1) × (n+1) dots), the total number of possible edges is 2n(n+1).
    • Since almost all edges are available, the branching factor is close to this total number of moves. For a 5 × 5 board, there are 2 ⋅ 5 ⋅ 6 = 60 potential moves, so the initial b ≈ 60.

  • Middle Game:

    • The Branching Factor starts to decrease as lines are drawn and removed from the pool of available moves.
    • However, sequences of scoring moves (extra turns) introduce local periods of very high branching factor, as the same player continues to move, effectively multiplying the depth in that sequence.

  • End Game:

    • The Branching Factor drops significantly. Many lines are already drawn.
    • The game often simplifies into a sequence of forced moves, where players have very few safe options and must strategically sacrifice turns, leading to b approaching 1 or 2.

  • Key Distinction: Branching Factor vs. Effective Branching Factor:

    • The Effective Branching Factor remains high in the early and mid-game, not just due to the number of moves, but because the extra turns complicate the Minimax search and push the necessary search depth deeper.

Question 4: Alpha-Beta Pruning Mechanics

  • Alpha-Beta Pruning is an optimization technique for the Minimax algorithm that eliminates unnecessary branches from the search tree.
  • It works by maintaining two bounds, Alpha (α) and Beta (β), which represent the best guaranteed scores found so far for the two players.

The Bounds

  • Alpha (α): This is the best score the maximizing player (Max, often the AI) can currently guarantee for themselves at the current level or above. Alpha starts at  − ∞.
  • Beta (β): This is the best score the minimizing player (Min, the opponent) can currently guarantee for themselves at the current level or above. Beta starts at  + ∞.

The Pruning Condition (Cutoff)

  • A cutoff (pruning) occurs when β ≤ α.
  • Rationale: If the minimizing player (Min) finds a move that results in a score (β) that is less than or equal to a score the maximizing player (Max) has already guaranteed for themselves (α) in a previously explored branch, the rest of the current branch is irrelevant.
  • Max knows that Min will never choose a path that leads to a score β if Max already has a better guaranteed option (α). Therefore, we can stop searching that branch without losing the optimal move.

2 × 2 Dots and Boxes Example (Simplified)

Consider a simple 2 × 2 grid (4 boxes total). The depth limit is small.

  • Scenario: Max is currently evaluating Move A, and the α value is 5 (meaning Max has already found a path guaranteeing a score of 5).
  • Min's Turn (Child of A):
    • Min explores Min's first option (A1) and it leads to a value of 8. β remains  + ∞.
    • Min explores Min's second option (A2) and it leads to a value of 4. Now, Min updates β to 4, because Min can guarantee a score of 4 or better (lower) from this point onward. (β = 4).
  • The Cutoff: Since β (4) is now less than or equal to the currently guaranteed α (5) for the maximizer (β ≤ α is true), we stop searching Min's remaining moves (e.g., A3, A4).
  • Result: Max knows Min will choose the path that results in a score of 4. Since Max already has a guaranteed path resulting in 5 (from Move B, for example), Move A is inferior, and the remaining branches of Move A are pruned.

Question 5: Minimax vs. Monte Carlo Tree Search (MCTS)

Why Minimax is Overly Computational Against a Random Opponent

  • Minimax is designed to find the absolute best move assuming the opponent will also play optimally (or near-optimally) to minimize the Minimax player's score.
  • This search requires a deep and exhaustive exploration of the game tree up to the maximum depth (d).
  • When the opponent plays randomly, the massive computational cost of searching deep, broad branches for the opponent's "best" (score-minimizing) reply is wasted.
  • Minimax still performs the full Alpha-Beta Pruning process, even though the random opponent won't necessarily choose the worst-case move that justifies the pruning.
  • The computational effort is spent optimizing against an ideal adversary, not the actual, random one.

Monte Carlo Tree Search (MCTS) as an Optimal Alternative

  • MCTS is a more effective search algorithm when facing random or unknown opponents, or when the game space is too large for deep exhaustive search.

  • Efficiency: MCTS trades off guaranteed optimality for fast, probabilistic decision-making by focusing search efforts on the most promising moves based on sampling.

  • Mechanism (The Four Steps): MCTS builds its search tree asymmetrically through repeated simulations, guided by probability:

    1. Selection: Starting from the root, it selects the most urgent (promising) child nodes using a selection policy, most often the Upper Confidence Bound 1 (UCB1) formula.
    2. Expansion: If the selected node has unvisited children, one child is chosen and added to the tree.
    3. Simulation (Rollout): A playout (simulation) is performed from the newly expanded node to the end of the game using a purely random (or simple heuristic) policy.
    4. Backpropagation: The result (Win/Loss/Draw) from the simulation is passed back up the tree, updating the visit count and win score stored in every node along the path.

  • Role of UCB1:

    • UCB1 balances Exploration (trying less visited moves) and Exploitation (focusing on moves with a high known win rate).
    • It mathematically ensures that the search effort is concentrated where the potential reward is highest, based on limited random sampling.
    • This probabilistic sampling avoids the deep, guaranteed worst-case search of Minimax, making it far faster when the opponent's responses are not guaranteed to be optimal.
